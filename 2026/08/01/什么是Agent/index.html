什么是 Agent？从大模型到自主行动系统

发表于2026-08-01|更新于2026-08-01|人工智能
|浏览量:

最近两年，Agent 几乎成为了 AI 领域最热门的词之一。

有人把能够调用工具的大模型称为 Agent，有人认为只有可以长期自主运行的系统才算 Agent，还有人把一套固定的自动化流程也叫作 Agent。概念越来越多，反而容易让人忽略它最核心的特征。

这篇文章尝试从工程视角回答一个基础问题：什么是 Agent？

一句话理解 Agent

AI Agent 是一个能够围绕目标持续观察环境、进行推理和规划、调用工具采取行动，并根据执行结果调整下一步策略的系统。

普通大模型主要完成的是“输入问题，生成回答”。

Agent 关注的则是“为了完成目标，接下来应该做什么”。它不仅产生文本，还可以查询资料、读取文件、调用接口、执行代码、操作数据库，甚至与其他 Agent 协作。

因此，可以把大模型看作 Agent 的“大脑”，但只有大脑还不等于一个完整的 Agent。

大模型和 Agent 有什么区别？

假设我们提出一个目标：

分析线上接口变慢的原因，并给出修复建议。

普通大模型只能根据提示中已有的信息进行分析。如果没有日志、监控数据和代码，它只能给出通用建议。

Agent 则可能执行下面的过程：

  1. 查询接口的监控指标。
  2. 找出延迟开始上升的时间点。
  3. 检索同一时间段的错误日志。
  4. 阅读相关服务代码和最近的提交记录。
  5. 判断问题可能来自慢 SQL、缓存失效或下游超时。
  6. 调用工具验证猜测。
  7. 汇总证据并给出修复方案。

两者的关键区别，不只是“回答得是否聪明”，而是系统有没有形成一个完整的行动闭环。

维度 普通大模型应用 Agent
核心任务 生成一次回答 持续完成一个目标
执行步骤 通常由用户决定 可以由模型动态决定
外部能力 主要依赖提示中的信息 可以调用搜索、代码、数据库等工具
状态 单轮或有限上下文 保存任务状态、历史行动和中间结果
反馈 输出后通常结束 根据工具结果继续调整
自主性 较低 在授权范围内具有一定自主性

Agent 的核心组成

一个真正可用的 Agent，通常不只是接入一个大模型接口，还需要下面几个部分。

1. 目标与指令

Agent 首先需要知道自己要完成什么，以及哪些事情不能做。

好的目标应当包含：

  • 最终需要交付的结果。
  • 可以使用的数据和工具。
  • 时间、成本与执行次数限制。
  • 权限边界和安全规则。
  • 判断任务完成的条件。

如果目标模糊，Agent 即使能力很强，也可能沿着错误方向不断尝试。

2. 模型与推理能力

大模型负责理解目标、分析上下文、拆分任务并决定下一步行动。

模型不一定需要一次生成完整计划。在复杂任务中，它可以先执行一个小步骤，观察结果，再决定后续动作。这种“边行动、边观察、边调整”的方式，通常比一次性规划全部步骤更适合不确定环境。

3. 工具

工具让 Agent 从“会说”变成“能做”。

常见工具包括：

  • 搜索引擎和知识库。
  • 数据库查询。
  • HTTP API。
  • 文件读取与写入。
  • 代码执行环境。
  • 浏览器、邮件和办公软件。
  • 监控、日志和发布平台。

工具本身通常是确定性的，Agent 的价值在于根据当前状态选择合适的工具，并正确组织参数。

4. 记忆与上下文

Agent 需要记住已经做过什么，避免重复执行或前后矛盾。

记忆可以分为：

  • 短期记忆：当前任务中的对话、计划、工具返回结果。
  • 长期记忆：跨任务保存的用户偏好、历史经验和知识。
  • 外部记忆：数据库、向量库、文件或知识图谱中的信息。

记忆越多并不一定越好。无关信息会增加上下文成本，也可能干扰模型判断，因此记忆系统需要检索、筛选和淘汰机制。

5. 规划与任务拆分

6. 观察、反馈与评估

Agent 每次采取行动后，都要读取执行结果。

工具可能返回成功数据，也可能返回错误、空结果或权限不足。Agent 需要判断：

  • 这一步是否成功？
  • 新信息是否支持原来的猜测？
  • 是否需要更换工具或参数？
  • 当前证据是否足以结束任务？
  • 是否应当请求人工确认？

如果没有反馈环节，系统只是按照顺序调用接口，并不具备真正的适应能力。

Workflow 和 Agent 不完全相同

Anthropic 在《Building Effective Agents》中专门区分了 Workflow 和 Agent。

Workflow 的执行路径主要由程序提前定义：

每一步做什么、下一步走向哪里，通常已经写在代码中。

Agent 的执行路径则由模型根据环境动态决定：

对比项 Workflow Agent
路径 预先编排 动态决策
可预测性 高 相对较低
灵活性 较低 较高
成本与延迟 容易控制 可能随执行步骤增加
适合场景 流程稳定、规则明确 步骤不确定、需要探索和判断

这两者没有绝对的优劣。

如果任务可以通过固定流程稳定解决，就没有必要为了“看起来更智能”而使用 Agent。很多生产系统更适合采用 Workflow 与 Agent 结合的方式：关键流程由代码控制，局部不确定环节交给模型决策。

Agent 可以做什么？

编程 Agent

编程 Agent 可以读取代码仓库、搜索调用关系、修改文件、运行测试并根据报错继续修复。

它与普通代码补全工具的区别在于：代码补全通常只生成一段代码，而编程 Agent 会围绕“让测试通过”或“完成需求”持续执行多个步骤。

研究 Agent

研究 Agent 可以把问题拆成多个方向，搜索不同来源，比较信息的可靠性，最后整理为结构化报告。

但研究结果仍需要来源追踪和事实校验，不能因为 Agent 搜索了很多网页，就默认结论一定正确。

客服与业务 Agent

客服 Agent 可以查询订单、阅读售后规则、判断问题类型，并在授权范围内执行退款、补偿或创建工单。

这类场景必须特别重视权限控制。回答错误和执行错误的影响完全不同：说错一句话可能还能纠正，错误地退款或修改数据则会直接产生业务损失。

运维 Agent

运维 Agent 可以结合监控、日志、链路追踪和变更记录排查故障，甚至执行预先批准的恢复操作。

较安全的做法通常是分级授权：

  • 读取数据可以自动执行。
  • 低风险操作需要记录和审计。
  • 发布、扩容、回滚等高风险操作需要人工确认。

什么是多 Agent 系统？

当一个 Agent 同时承担规划、搜索、编码、审核和执行等任务时，提示和上下文会越来越复杂。

多 Agent 系统会把不同职责分给不同角色，例如：

  • Planner：负责拆分任务和制定计划。
  • Researcher：负责搜索和整理资料。
  • Coder：负责实现代码。
  • Reviewer：负责检查结果和发现风险。
  • Executor：负责执行经过批准的操作。

多 Agent 的优势是职责清晰、可以并行工作，但它也引入了新的问题：

  • Agent 之间如何传递上下文？
  • 出现冲突时听谁的？
  • 如何避免重复工作？
  • 如何追踪每个结论的来源？
  • 多次模型调用带来的成本是否值得？

因此，多 Agent 并不是 Agent 数量越多越好，而应当根据任务边界和并行价值进行设计。

Agent 面临哪些问题？

1. 错误会在循环中累积

普通模型回答错误，影响通常停留在一次输出中。

Agent 的错误可能被后续步骤当作事实继续使用，最终形成连锁错误。例如错误理解日志后，又根据错误结论修改代码并发布。

2. 工具调用带来真实风险

Agent 能力越强，可以影响的外部系统就越多。

文件删除、数据库修改、邮件发送、资金操作和线上发布都需要最小权限、操作审计、参数校验和人工审批。

3. 成本与延迟不稳定

Agent 为了完成任务可能反复推理和调用工具。执行步数越多，模型费用、外部 API 费用和响应时间就越难预测。

生产系统通常需要设置：

  • 最大执行步数。
  • 最大 Token 或费用预算。
  • 单个工具超时时间。
  • 重试次数。
  • 全局任务截止时间。

4. Prompt Injection

当 Agent 阅读网页、邮件或外部文档时，内容中可能包含恶意指令，例如要求 Agent 忽略原有规则并泄露数据。

外部内容应当被视为“不可信数据”，而不是系统指令。工具权限、敏感信息和执行策略不能只依赖模型自行判断。

5. 评估比聊天应用更困难

评估 Agent 不能只看最终回答是否流畅，还需要检查：

  • 是否完成了目标？
  • 使用的步骤是否合理？
  • 是否调用了不必要的工具？
  • 结论有没有证据支持？
  • 失败时能否安全退出？
  • 执行成本和耗时是否可接受？

Agent 的测试更像是对一个动态系统进行评估，而不只是比较一句文本答案。

什么时候适合使用 Agent？

Agent 更适合下面这些任务：

  • 目标明确，但完成路径无法完全提前确定。
  • 需要在多个信息源和工具之间来回操作。
  • 中间结果会影响下一步决策。
  • 任务允许试错，并且可以验证结果。
  • 人工完成需要大量重复的信息收集和判断。

下面这些情况通常不需要 Agent：

  • 一个简单函数或 SQL 就能解决的问题。
  • 步骤固定且必须严格按照流程执行。
  • 对延迟和成本极其敏感。
  • 错误后果很严重，却没有审批和回滚机制。
  • 无法判断结果是否正确。

一个实用原则是：

先尝试最简单、最可控的方案，只有当固定流程无法处理任务中的不确定性时，再逐步增加 Agent 的自主能力。

总结

Agent 并不是某个单独的模型，也不是“给大模型加几个工具”这么简单。

它更像一个围绕目标运行的软件系统：

  • 大模型负责理解、推理和决策。
  • 工具负责读取信息与执行动作。
  • 记忆保存任务状态和历史经验。
  • 规划负责拆分目标。
  • 反馈循环帮助系统根据结果持续调整。
  • 权限、评估和审计保证它不会无限制地行动。

真正有价值的 Agent，不是表现得最像人，而是能够在清晰边界内，可靠地完成过去需要人反复操作和判断的任务。

Agent 的未来也许会非常强大，但在工程实践中，可控、可验证、可观察，往往比“完全自主”更加重要。
