从零写两份 Agent Skill：Java 代码审查与 Hexo 博客发布

发表于2026-10-09|更新于2026-10-09|人工智能
|浏览量:

面试中被问到“有没有写过 Skill”，只了解概念通常还不够。更有说服力的回答，是能讲清楚：它解决什么重复任务、怎样组织指令和资源、如何控制触发范围，以及做过哪些验证。

这篇文章从两个实际场景出发，制作 Java 后端代码审查 和 Hexo 技术博客写作与发布 两份 Skill。示例由 AI 辅助编写，附有实际文件、校验脚本和下载包，适合作为练习起点。

本文以 Codex 的本地 Skill 为实现环境。其他 Agent 产品也可能支持类似规范，但安装位置、工具和元数据支持需要查对应平台文档。

1. Skill 是什么？

Skill 是可复用的任务知识与执行流程包，由指令、参考资料和可选的脚本或模板组成，帮助 Agent 在特定场景下稳定完成工作。

它与一次性的 Prompt 都使用自然语言指导模型，但 Skill 把触发条件、操作流程和辅助资源组织成可维护的目录，方便跨任务复用。

Skill 也不等于一个独立 Agent：它不必拥有自己的模型、后台进程或执行循环。Agent 在运行过程中选用合适的 Skill，读取相关说明，再利用环境提供的工具完成任务。

对于“解释什么是事务”这种简单问题，普通提问就够了；对于“每次代码审查都要跟踪鉴权和事务调用路径、按证据报告问题”，Skill 更有价值。

2. Skill 的组成

一个 Skill 的最小结构只有一个文件：

需要辅助资源时，可以扩展为：

组成 必需吗 作用
SKILL.md 必需 YAML 元信息与核心操作指令
references/ 可选 按需读取的领域规则、数据结构和细节
scripts/ 可选 执行确定性的转换或校验逻辑
assets/ 可选 用于输出的模板、图片等资源
agents/openai.yaml 可选 Codex 平台的展示信息、调用策略和工具依赖等

不要为了凑齐结构创建空目录。一份简短、聚焦的 Skill 可能只需要 SKILL.md。

YAML 元信息：决定什么时候考虑使用

SKILL.md 开头需要 name 和 description：

name 应简短、清晰，使用小写字母、数字和连字符。description 要说清能力和适用场景，必要时增加容易混淆的排除范围。

“用于编程相关问题”范围过大；“审查 Java/Spring 后端变更中的实际缺陷”更容易被准确匹配。

Markdown 正文：指导怎么做

正文应描述实际输入、关键步骤、约束和输出。例如：

  • 从用户指定的提交或差异确定范围。
  • 读取相关调用方，而不是只看修改行。
  • 依据触发条件和证据报告问题。
  • 审查默认只读，不擅自提交或部署。

重点是补充会影响决策的知识，而不是反复要求“认真分析、专业回答”。

3. 渐进式披露：按需加载

官方文档介绍了 Skill 的渐进式披露机制：[1]

  1. 选择技能时，先提供 name 和 description 等简短信息。
  2. 决定使用后，再读取完整 SKILL.md。
  3. 只有当前任务需要时，才加载参考资料或执行脚本。

因此，一份好的 Skill 应把公共流程留在入口，把较长的条件性知识移到 references。

脚本与参考资料也有区别：脚本是可执行代码，往往可以直接运行；references 是供模型读取的知识。两者都需要明确的调用说明，而不是仅仅放在目录里。

4. 示例一：Java 后端代码审查

解决什么问题？

代码审查容易出现两种情况：

  • 只检查格式与命名，没有发现行为缺陷。
  • 看到某种写法就判断“有 Bug”，却没有确认运行条件。

这份 Skill 把关注点放在鉴权、事务、并发、缓存和异常处理，并要求每项发现有可核对的证据。

目录结构

完整 SKILL.md

references 中写什么？

backend-risks.md 提供按场景读取的审查线索，例如：

  • 鉴权：用户 ID 是否来自可信身份，查询是否限制资源所有权。
  • 事务：是否经过事务代理，异常是否被吞掉，外部服务是否超出事务边界。
  • 并发：先查后写是否存在竞争，唯一约束是否覆盖风险。
  • 缓存：缓存键是否包含租户维度，失效策略是否会产生陈旧值。
  • 外部调用：超时和重试是否产生重复副作用。

它特别注明：这些是排查线索，不是自动成立的缺陷。例如 Spring 同类自调用的事务问题需要确认实际代理模式，不能只看到方法调用就下结论。

使用示例

假设查询直接接受请求中的 userId，而没有绑定登录用户，Skill 应引导 Agent 阅读鉴权入口和数据库查询，判断能否构造越权请求，再报告具体位置与影响。

这是预期工作方式示例，不是本次已经运行的生产系统审查结果。

5. 示例二：Hexo 技术博客写作与发布

解决什么问题？

技术文章发布不仅要生成文字，还需要处理：

  • 来源是否可靠、是否真的访问过。
  • YAML 标题与日期是否有效。
  • Markdown 代码块是否闭合。
  • Hexo 是否成功生成文章。
  • 部署成功后，线上是否真的出现新内容。

这份 Skill 把写作、检查和发布串起来，同时区分用户只是要草稿，还是明确要求上线。

目录结构

完整 SKILL.md

为什么附带脚本？

文章标题是否为空、日期是否有效、代码块是否闭合，这些检查适合用程序执行，而不是让模型每次凭感觉检查。

check-post.cjs 会：

  • 确认文件实际位于指定 Hexo 站点的 source/_posts 内。
  • 检查 UTF-8、YAML 元信息、非空标题与正文。
  • 校验日期及可选的时分秒。
  • 检查常见 Markdown 围栏代码块是否闭合。
  • 检查失败时返回非零退出码。

脚本只读取文件，不部署、不修改文章、不访问网络。YAML 解析使用站点已经安装的 js-yaml，缺少依赖时报告错误，不静默安装。

支持的日期格式为 YYYY-MM-DD 或 YYYY-MM-DD HH:mm:ss，也接受 T 分隔。这是示例脚本的校验范围，不代表 Hexo 只支持这些日期格式。

6. 下载与安装

下载两份 Skill 的完整 ZIP 包

压缩包包括两份 SKILL.md、对应参考资料和只读文章检查脚本，不包含凭证或个人账户配置。

本博客源码仓库已经将两份 Skill 放在 .agents/skills 下。按当前 Codex 官方文档，仓库内的 .agents/skills 可用于本地发现。[1]

在其他项目中使用时，把对应目录放入项目根目录的 .agents/skills：

显式调用可以使用 $skill-name；平台也可能依据 description 自动选择。不同客户端的选择入口有所区别，例如 CLI/IDE 的技能选择或桌面端技能界面。未发现新 Skill 时，检查目录与元信息，必要时重启客户端。

这些文件不会自动安装工具或获取权限：审查需要代码读取能力，博客发布需要对应的构建环境和现有部署授权。要分发为插件，可以按平台规范进一步打包；本例先采用适合本地练习的目录与 ZIP。

7. 本次做了哪些验证？

本次验证分为格式和脚本行为两部分：

  • 两份 Skill 的 YAML 均能解析，name 与目录一致，description 有效。
  • SKILL.md 引用的参考文件均存在。
  • 脚本通过 13 个正常与异常用例，覆盖纯日期、日期时间、代码块、非法日期和时间、缺少标题、坏 YAML、空正文、目录越界、错误编码，以及失败退出码。
  • 脚本成功检查现有 Agent 和 Harness 两篇文章。

校验工具使用 Hexo 现有的 js-yaml，没有为验证额外安装 Python YAML 依赖。

这些结果证明了格式和检查脚本的部分行为，还不能证明 Agent 会在所有实际任务中准确触发或做出正确判断。本次也没有把示例应用于生产 Java 项目，或独立重复完整博客发布流程来作对比评估。

下一步应针对真实任务验证：

验证维度 示例
正例触发 请求审查订单接口时，是否选择代码审查 Skill
反例触发 只问事务概念时，是否避免进入仓库审查流程
范围控制 只要草稿时，是否不部署、不推送
判断质量 是否提供有效证据，而非机械罗列清单
异常处理 构建失败时，是否停止后续部署并说明原因

需要比较效果时，可以使用相同任务记录启用前后的结果，而不是用未经测量的“效率提高 80%”来描述收益。

8. 写 Skill 时的注意点

聚焦一个任务

不要把代码审查、前端设计、论文写作和数据库运维塞进一个 Skill。职责越清楚，触发和维护越容易。

说明输入与输出

“审查代码”不够具体，应明确审查范围怎么确定、缺陷怎样给证据、结果怎样表达。

不让 Skill 擅自扩大授权

Skill 说明执行流程，不授予额外权限。读取代码、写草稿、发布页面、推送源码是不同动作，要根据用户当前请求和已有授权判断。

规则放在正确位置

模型负责需要判断的工作；脚本负责可确定的机械检查。密码和 Token 放在合适的凭证管理环境中，不写进 SKILL.md、参考资料或下载包。

让参考资料真正按需加载

如果每次都读取所有 references，就失去了节约上下文的作用。在入口说明什么时候读取哪份资料。

检查脚本不会替代业务验证

检查通过只说明满足相应规则，不代表文章事实正确，也不代表系统没有缺陷。像越权、事务和幂等问题，需要真实上下文与针对性验证。

保持环境适配

不要在可复用 Skill 中写死机器目录、GitHub 用户名、分支或构建方式。读取用户项目现有配置，缺少关键条件时明确说明。

9. 面试中怎么讲？

完成示例后，应先亲自读懂文件，并至少运行一个实际任务，再把经验转化成自己的表达。

可以这样概括：

我最近做了两份 AI 辅助编写的 Skill 示例：Java 后端代码审查和 Hexo 技术博客写作发布。使用 SKILL.md 定义名称、触发范围和流程，把细节拆到 references，并用只读脚本校验文章格式。完成了元信息和脚本用例检查，目前还在真实任务中验证触发与效果。

面试官继续追问时，可以围绕四点展开：

  1. 为什么写？ 把重复工作中的关键步骤和领域规则沉淀下来。
  2. 如何组成？ 必需的 SKILL.md，加上有实际用途的可选资源。
  3. 如何避免误用？ 清晰 description、范围约束和执行授权。
  4. 如何验证？ 格式检查、脚本测试，以及真实任务的正例与反例。

如果只是运行一次示例，不应说“已经长期用于团队生产流程”。能够诚实说明设计、验证和限制，比背诵概念更有说服力。
